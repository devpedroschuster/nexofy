# Lista de espera automática para turma lotada

Data: 2026-09-13
Status: aprovado (decisões-chave validadas com o usuário) — em implementação

## Contexto

Item do roadmap "Nexofy HQ" (fonte: Análise Competitiva "Nexofy vs. Mercado
Fitness", 10/09/2026, seção 5 — Lacunas ou Pontos Cegos): nenhum dos 5
concorrentes analisados documenta fila de espera automática, então a barra
aqui é o padrão geral do mercado fitness (Mindbody, ClassPass, WellnessLiving),
não um concorrente específico — fechar uma lacuna de UX própria.

Hoje, quando uma turma está lotada, `agendar_avulso` só emite o erro
`P0100` ("Turma lotada") — sem fila, sem forma de o aluno demonstrar
interesse e ser avisado quando uma vaga abrir.

## Pré-requisito descoberto durante o levantamento

Havia 3 migrations e a edge function `criar-cobranca-asaas` já modificadas
na `main`, sem commit, implementando o self-service de agendamento do app
mobile (`agendar_avulso`/`cancelar_agendamento` liberados para o próprio
aluno, regras de antecedência e inadimplência configuráveis por estúdio).
Essas mudanças já tinham sido validadas em staging (comentários citam
`get_advisors`) mas nunca commitadas. A lista de espera depende diretamente
desse `agendar_avulso` (P0100/P0101/P0102). Decisão validada com o usuário:
commitar esse trabalho pendente primeiro (commit `fb12d57` na `main`,
cherry-pick para esta branch), em vez de duplicar a lógica.

Também descoberto (fora de escopo, sinalizado como tarefa separada via
`spawn_task`, não corrigido aqui): `AreaAluno.jsx` (autoatendimento web)
chama a RPC inexistente `agendar_aula` (PED-185, já conhecido — o app
mobile em desenvolvimento já corrigiu isso do lado dele) — **este sim
precisa ser corrigido aqui**, porque sem ele não há como testar/entregar
o ponto de entrada da fila de espera no autoatendimento. Além disso, a
leitura de `presencas` embutida em `agenda` nessa mesma tela nunca retorna
linhas para um aluno real (RLS de `presencas` só libera `estudio_membros`)
e `agenda.vagas_ocupadas` nunca é atualizado por nada no schema — os dois
tornam o indicador de "Esgotado"/"Agendado" mostrado ao aluno antes do
clique não confiável. Isso é pré-existente e ortogonal à fila de espera
(a validação real de capacidade já acontece no servidor via
`verificar_disponibilidade_v2`/`agendar_avulso`, então a fila de espera
funciona corretamente mesmo com esse indicador desatualizado) — por isso
foi apenas sinalizado, não corrigido nesta entrega.

## Decisões validadas com o usuário

| Decisão | Escolha |
|---|---|
| Baseline da worktree | Commitar o self-service pendente na `main` antes de abrir a branch da feature |
| Mecanismo de promoção | Auto-agendar o próximo da fila diretamente (não oferta com prazo de confirmação) + notificar + cancelamento fácil |
| Escopo de UI | Web only: painel do estúdio (Agenda) + autoatendimento (AreaAluno.jsx). App mobile fica de fora (já registrado como V1.1 com spec própria no design doc de 2026-09-09) |

## Modelo de dados

Nova tabela `lista_espera` (nomenclatura em português, consistente com
`agenda_fixa`/`agenda_excecoes`):

```sql
create table public.lista_espera (
  id bigint generated by default as identity primary key,
  estudio_id uuid not null references public.estudios(id),
  aula_id bigint not null references public.agenda(id),
  data_aula date not null,
  aluno_id bigint not null references public.alunos(id),
  status text not null default 'aguardando'
    check (status in ('aguardando','convertido','cancelado','expirado')),
  criado_em timestamptz not null default now(),
  promovido_em timestamptz,
  notificado_em timestamptz,
  presenca_id bigint references public.presencas(id),
  motivo_saida text
);

-- só 1 entrada ativa por aluno/turma/data; permite reentrar após sair/expirar
create unique index lista_espera_ativa_uniq on public.lista_espera
  (estudio_id, aula_id, data_aula, aluno_id) where (status = 'aguardando');

create index lista_espera_fila_idx on public.lista_espera
  (estudio_id, aula_id, data_aula, status, criado_em);
```

RLS: mesma convenção de `presencas` — só `estudio_membros`
(admin/professor/super_admin) tem policy direta na tabela. O aluno nunca
lê/escreve a tabela diretamente; toda a superfície dele passa por RPCs
`SECURITY DEFINER` com checagem explícita de propriedade (mesmo padrão de
`agendar_avulso`/`cancelar_agendamento`).

## Refatoração de suporte (DRY)

`verificar_disponibilidade_v2` computa ocupação (avulsos/leads + fixos sem
falta) inline. Extraio isso para `calcular_ocupacao_turma(p_aula_id,
p_data, p_estudio_id) returns table(ocupacao_atual int, capacidade_max int)`
e ambos — `verificar_disponibilidade_v2` e a função de promoção da fila —
passam a chamar essa função, em vez de duplicar a query. Mantém o shape de
retorno JSON de `verificar_disponibilidade_v2` inalterado.

## RPCs novas

- `entrar_lista_espera(p_estudio_id, p_aluno_id, p_aula_id, p_data_aula)`
  — mesma checagem de autorização de `agendar_avulso` (próprio aluno ou
  admin/professor/super_admin); rejeita se o aluno já está agendado nessa
  turma/data, se já está `aguardando`, ou se a turma na verdade não está
  lotada (nesse caso deveria agendar direto). Retorna a linha criada.
- `sair_lista_espera(p_estudio_id, p_lista_espera_id)` — dono ou staff;
  marca `cancelado`.
- `listar_minha_fila(p_estudio_id, p_aluno_id)` — retorna as entradas do
  aluno (aguardando com posição calculada via `row_number()`, e as
  recentes convertidas/expiradas/canceladas) para a tela dele.

Leitura do lado do estúdio (admin) usa `select` direto na tabela (RLS já
cobre `estudio_membros`), sem RPC dedicada.

## Promoção automática

Trigger `AFTER INSERT OR UPDATE OR DELETE ON presencas` chama
`promover_fila_apos_liberar_vaga()` (`SECURITY DEFINER`) quando a mudança
libera uma vaga:
- `DELETE` de uma linha avulso/lead com status `agendado`/`presente`
  (cancelamento);
- `UPDATE` de avulso/lead de `agendado`/`presente` para
  `falta_justificada`/`falta_nao_avisada` (falta registrada);
- `INSERT` de uma linha `fixo` já nascendo com falta (falta antecipada de
  matrícula fixa, fluxo real documentado em `lembretes-aula`).

A função toma o mesmo advisory lock (`aula_id`+`data_aula`) usado por
`agendar_avulso`, e então, em loop, enquanto houver vaga: pega o
`aguardando` mais antigo, revalida com `verificar_disponibilidade_v2`
(fora do plano → marca `expirado`, motivo `fora_do_plano`, tenta o
próximo) e a mesma checagem de inadimplência de `agendar_avulso` (marca
`expirado`, motivo `inadimplente`, tenta o próximo); se elegível, insere
em `presencas` (`avulso`/`agendado`) e marca a entrada `convertido` com
`presenca_id`. O insert que a própria função faz tem status `agendado`,
que não bate em nenhuma das 3 condições de "liberou vaga" acima — sem
recursão.

Não cobre (fora de escopo, YAGNI): aumento manual de capacidade da turma
promovendo a fila automaticamente — caso raro, admin pode agir manualmente.

## Notificação

Sem chamada HTTP direta de dentro do trigger (sem precedente no repo, e
exigiria Vault dentro do Postgres). Segue o padrão já estabelecido por
`lembretes-aula`/`gerar-mensalidades`: nova edge function
`lista-espera-notificacoes`, chamada por `pg_cron` (setup manual via
RUNBOOK.md, replicado em staging e produção — mesma convenção das cron
jobs existentes), que:
1. Busca `lista_espera` com `status = 'convertido' AND notificado_em IS NULL`,
   envia push Expo (reaproveita o padrão de lote de `lembretes-aula`) e
   marca `notificado_em`.
2. Varre `status = 'aguardando' AND data_aula < current_date` e marca
   `expirado` (motivo `data_passada`) — limpeza de filas de turmas que já
   aconteceram.

Push é best-effort (só alcança quem já usa o app mobile, que ainda não
foi lançado) — por isso a UI web do aluno (abaixo) é o canal garantido.

## Frontend

**Admin (`webapp/src/pages/Agenda`)**: no modal de lotação
(`ModalAgendamento.jsx`), quando `tipo === 'lotacao'` e o agendamento é de
um aluno cadastrado (não visitante — lista de espera exige `aluno_id`),
mostra uma terceira opção "Adicionar à lista de espera" ao lado de
"Agendar mesmo assim"/"Cancelar" (estendo `ModalConfirmacao` com uma ação
extra opcional, sem quebrar os demais usos). Um painel de
visualização/gestão da fila (nomes em ordem, remover manualmente) fica de
fora do V1 — o valor central do recurso é não exigir intervenção manual do
estúdio; um painel de leitura pode ser adicionado depois se pedido.

**Autoatendimento (`webapp/src/pages/AreaAluno.jsx`)**: primeiro corrige o
bug bloqueante (RPC `agendar_aula` inexistente → `agendar_avulso`;
`cancelar_agendamento` com os 4 parâmetros corretos), replicando a correção
já validada no app mobile (`mobile/src/features/agenda.ts`). Depois, ao
capturar o erro `P0100` de `handleAgendar`, oferece "Entrar na lista de
espera" (chama `entrar_lista_espera`) em vez do toast genérico atual.
Adiciona também uma pequena seção "Minha lista de espera" (via
`listar_minha_fila`) mostrando posição e permitindo sair.
