## PED-22 — backup: bug real encontrado e corrigido, resto continua bloqueado

Estado herdado da auditoria de 26/08
([`2026-08-26-ped20-23-banco-rls-auditoria.md`](2026-08-26-ped20-23-banco-rls-auditoria.md)):
org no plano free do Supabase, sem PITR nem backup diário nativo. Stopgap
(`.github/workflows/db-backup.yml`, `pg_dump` diário via GitHub Actions)
já existia. Em vez de confiar no documento anterior como estado atual,
comparei contra a realidade (GitHub Actions, secrets, advisors) — foi assim
que apareceu o bug abaixo, que o documento de 26/08 não previa.

**Verificação nesta sessão:**
- `gh secret list` confirma que `STAGING_DB_URL` existe (criado 27/08), mas
  **`PRODUCTION_DB_URL` continua ausente**.
- `gh run list --workflow=db-backup.yml` mostra as 3 execuções agendadas
  desde a criação (27, 28 e 29/08) — **todas falharam**.
- **A causa da falha não é a que eu esperava — e eram 3 bugs em cascata,
  não 1.** Só apareceram um de cada vez, cada um mascarando o próximo até
  ser corrigido. Todos encontrados e corrigidos disparando o workflow de
  verdade (`gh workflow run` + `gh run watch`) nesta branch, não só lendo o
  YAML:

  1. **`apt-get install -y postgresql-client-17` falhava** com
     `E: Unable to locate package postgresql-client-17` — o runner
     `ubuntu-24.04` só traz `postgresql-client-16` no repositório padrão; a
     versão 17 exige o repositório oficial `apt.postgresql.org` (PGDG).
     Corrigido instalando `postgresql-common` e rodando o script oficial
     `/usr/share/postgresql-common/pgdg/apt.postgresql.org.sh` antes —
     método recomendado pelo próprio projeto PostgreSQL.
  2. **Corrigido o passo 1, mas o `pg_dump` continuava rodando a versão
     16** (`pg_dump: error: aborting because of server version mismatch` —
     servidor 17.6, client 16.15) — o runner já vem com
     `postgresql-client-16` pré-instalado, e o `pg_dump` genérico do PATH
     resolvia pra ele mesmo com o 17 também instalado. Corrigido chamando o
     binário versionado direto: `/usr/lib/postgresql/17/bin/pg_dump`.
  3. **Corrigidos os passos 1-2, mas o matrix (`staging`/`production`)
     usa `fail-fast: true` por padrão** — como produção falha rápido (secret
     ausente), a perna de staging era cancelada no meio antes de terminar,
     mesmo já funcionando de ponta a ponta. Corrigido com
     `fail-fast: false`: as duas pernas agora rodam independentes, do jeito
     que backup de ambientes diferentes deveria funcionar.

**✅ Corrigido e validado de ponta a ponta:** depois dos 3 fixes, disparei o
workflow mais uma vez nesta branch — `backup (staging)` completa 100% verde
(instala o client certo, `pg_dump` roda, artifact é enviado); `backup
(production)` falha exatamente no ponto esperado e documentado (secret
ausente), sem mais nenhum erro incidental escondido atrás dele.

**Continua bloqueado, ação do Pedro (credenciais — não posso fazer):**
1. Criar o secret `PRODUCTION_DB_URL` no GitHub (`STAGING_DB_URL` já existe) —
   connection string em Dashboard → Settings → Database. Depois disso, a
   execução agendada seguinte já deve completar nos dois ambientes — os 3
   bugs de CI que impediam isso foram corrigidos e validados nesta sessão.
2. Testar um restore real (`pg_restore` contra um projeto/branch de teste,
   nunca staging/produção direto) — exigência explícita do ticket, ainda não
   feita.
3. Decidir sobre upgrade de plano para PITR nativo (o stopgap não é
   equivalente — sem retenção contínua, sem restore de 1 clique).
